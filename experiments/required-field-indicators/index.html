UI Experiments / Required-field indicators

Required-field concepts

Eleven ways to show what's needed before someone presses Submit, without asterisks. Each form is live: type, tab through, and skip fields to see how it responds. They all start from the same baseline form, which uses asterisks.

Split sections

The layout answers the question. Required fields sit together under one heading, and everything optional is tucked behind "Add more details".

Before submit, users see

  • A live "2 of 4 done" count on the required group
  • Optional fields hidden until asked for, so nobody fills them by accident

Trade-offs

  • Very quiet; no per-field markers at all
  • Field order follows required/optional rather than topic

The essentials

Countdown button

Fields keep their natural order. The Submit button tracks what's left, and a "Still needed" line names the missing fields. Tap a name to jump to it.

Before submit, users see

  • A segmented meter and "4 required fields left" on the button
  • "Optional" placeholder text inside the fields that can be skipped
  • "Everything else is optional" once the required fields are done

Trade-offs

  • The signal lives at the bottom; on long forms it may be offscreen
  • Optional placeholder disappears once someone types

Progress rail

A thin rail runs down the form. Required fields get a ring that fills with a check when the answer is valid. Optional fields get a small dot.

Before submit, users see

  • Which fields matter, scannable down the left edge
  • Empty rings show a skipped required field right away
  • A milestone line that turns green when the required fields are done

Trade-offs

  • Needs a two-item legend the first time
  • Adds a visual element to every row

Visual weight

Styling alone tells the fields apart. Required fields are full strength. Optional fields recede: muted labels, a sunken fill, no border until focused.

Before submit, users see

  • An accent edge on every required field that's still empty or invalid
  • The edge clears as each answer becomes valid, so leftover edges are what's left to do

Trade-offs

  • The most "invisible" option; it relies on contrast, so it needs care for low-vision users
  • Screen readers still get aria-required, but sighted users get no words

The faded fields are extras. Fill them only if they help.

One at a time

One question per screen. Whether a question is optional shows up in the controls: optional questions have a Skip button, required ones don't.

Before submit, users see

  • Continue checks the answer right away, so nothing is found missing at the end
  • A progress bar that marks answered questions solid and skipped ones hollow

Trade-offs

  • Slower for short forms; people can't scan the whole thing
  • Suits mobile and first-time flows more than forms people fill often

Add-on chips

Only the required fields are on the form. Each optional field is a dashed chip that adds the field when tapped, and a Remove link takes it away again.

Before submit, users see

  • A short form where every visible field is needed, so there's nothing to label
  • Optional extras are opt-in, one at a time, so nobody fills them by accident
  • Submit stays dimmed until the required fields are valid

Trade-offs

  • Optional fields are easy to miss if you actually want people to fill them in
  • Works best when there are only a few optional fields

Fill-in sentence

The form reads as a short note. Everything required is part of the main sentence. Optional details sit in a lighter P.S. underneath, which people already understand as extra.

Before submit, users see

  • Empty blanks make the main sentence read as unfinished
  • A count under the sentence, which changes to "That's all we need" when it's complete

Trade-offs

  • Only suits short, conversational forms
  • Hard to translate, since word order changes by language
  • Error messages need room under each blank

Hi, my name is and you can reach me at . I'm writing about .

P.S. Only if it helps

Live preview

A card beside the form shows what will be sent, filling in as people type. Required items that are still empty appear as dashed "Needed" slots. Optional extras only appear once someone adds them.

Before submit, users see

  • A card header that reads "3 missing" until it says "Ready to send"
  • Tapping a missing slot jumps to its field
  • "None added" under Extras, which tells people the rest can stay empty

Trade-offs

  • Takes horizontal space; on phones the card sits above the form and scrolls away
  • Best when the submission has a natural summary, like an order, booking or message

Extras

Spotlight

No markers anywhere. The next required field gets a soft highlight and a "Next" tag. If someone moves past a required field without filling it in, the tag on it changes to "Skipped" and the highlight stays there. Once everything required is done, the highlight moves to Submit.

Before submit, users see

  • Where to go next, one field at a time
  • A "Skipped" tag on any required field they passed
  • "Optional. Skip it if you like." under an optional field while they're in it

Trade-offs

  • Shows one thing at a time, so people can't see the full list of what's needed up front
  • A highlight that keeps moving can distract; it has to stay subtle

Glow on entry

No markers while the form sits still. Each time someone moves into a field, every required field that still needs an answer glows briefly in a quick top-to-bottom wave, then the form goes quiet again.

Before submit, users see

  • What's still needed, every time they move to a new field
  • Finished fields drop out of the glow, so it shrinks as they go
  • The field they're in doesn't glow; it already has the focus ring
  • When nothing required is left, Submit glows instead

Trade-offs

  • Fields scrolled out of view glow where nobody can see them
  • Repeats on every move, which may feel busy on long forms; it could run only for the first few moves, or only after a required field is skipped
  • With reduced motion turned on, it becomes a brief color change with no spreading ring

Label on entry

Labels stay plain while the form sits still. When someone moves into an optional field, "(optional)" fades in after its label, and it fades out again when they leave. Required fields never change.

Before submit, users see

  • The word "optional" at the moment they decide whether to fill a field
  • A clean form at rest, with no markers or extra text

Trade-offs

  • People only find out a field is optional after they're in it, so they can't skim ahead
  • It doesn't flag a skipped required field on its own; it pairs well with J (Glow on entry)
  • Screen readers always hear "optional" in the label, since the visible word comes and goes
